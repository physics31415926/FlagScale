# 历史与压缩

## 概述

历史系统管理对话上下文窗口——追踪 Token 使用量、在超出预算时触发压缩、并在压缩过程中保留关键信息。

## HistoryManager

### Token 预算
- 通过 tiktoken 估算每条消息的 Token 数
- 维护运行总量，对比 `max_context_tokens`
- 超出阈值时触发压缩

### 压缩触发条件
- **轮内压缩**：阈值 0.70，目标 0.50
- **强制压缩**：阈值 0.90，目标 0.50
- **压缩比例**：`[0.60, 0.50, 0.40, 0.35]` — 逐步更激进

### 摘要管理
- 摘要上限：`max_context_tokens * 0.05`（如 200K 上下文 = 10K Token）
- 旧摘要段落融合（合并）而非丢弃
- 防止摘要在多次压缩后无限增长

### 膨胀比率
- 追踪压缩后消息重新摘要时的膨胀程度
- 使用 EMA：`0.7 * old + 0.3 * new`
- 异常值（>3.0）被丢弃，防止估算失控

### 硬上限截断
- 压缩后仍超预算时，按启发式评分分配截断预算：
  - 高分消息：1200 字符
  - 中分消息：600 字符
  - 低分消息：200 字符

## CompactionMixin

### 评分器
- 对每条消息评分（0.0–1.0）用于保留决策
- 容错：评分数量与消息数差值在 ±10% 内时截断/填充对齐
- 之前：任何不匹配直接放弃评分（丢失所有评分信息）

### 压缩前记忆转储
丢弃消息前，扫描提取：
- 关键决策和发现
- 已尝试的修复方案（提取并存储）
- 错误模式及其解决方案
- 写入 `SessionMemory` 和 `ExperimentManager.learnings`
- 压缩检查点使用 `priority="critical"`（7 天 TTL，自动清理）

### 压缩锚点
- 跨压缩保留计划状态（当前步骤标题 + 状态）
- 保留技能上下文和阶段信息
- 使用 `get('title')` 字段（修复了之前 `get('text')` 的 bug）

## 数据流

```
消息加入历史
    → Token 计数更新
    → 检查：总量 > 轮内阈值？
        是 → 评分消息 → 丢弃最低分
             → 记忆转储提取信息
             → 重建摘要
    → 检查：总量 > 强制压缩阈值？
        是 → 激进压缩（比例 0.35）
             → 发现失败尝试时注入警告
```

## 关键设计决策

1. **首次压缩即激进**：0.60 比例立即释放 40%（原为 0.80）
2. **永不丢失修复历史**：已尝试修复在丢弃前同步到 ExperimentManager
3. **评分器容错**：部分评分优于无评分
4. **摘要融合**：旧摘要合并到新摘要中，而非直接丢弃
